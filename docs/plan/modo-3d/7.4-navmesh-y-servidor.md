# 7.4 — Navmesh (`nav3d`) y movimiento 3D en el servidor

Lee antes: `docs/plan/fase-7-modo-3d.md` (§«Normas comunes») y `docs/specs/27-modo-3d.md` §2, §4,
§5 y §6. Requiere 7.1a integrado.

## Qué entrega

1. Un paquete nuevo, `@escaperoom/nav3d`, que construye la navmesh de una habitación 3D a partir
   del `RoomPackage` y el catálogo de modelos, y responde a tres preguntas: punto más cercano,
   ruta entre dos puntos y deslizamiento por la superficie. Funciona igual en Node y en el
   navegador.
2. El servidor de partida (`colyseus-server`) valida el movimiento de las salas 3D contra esa
   navmesh y sincroniza altura y giro de cada jugador.
3. El cliente de sesión (`game-runtime/session`) envía y expone altura y giro.

Las salas 2D no cambian en nada.

## Paso 0 — Prueba de arranque (antes de todo lo demás)

Crea el paquete con solo esto y comprueba que pasa:

  `exports: { ".": "./src/index.ts" }`, mismos scripts `lint` / `typecheck` / `test` que
  `packages/editor`), `tsconfig.json` y `vitest.config.ts` copiados de `packages/editor` y
  ajustados.
- Dependencia `recast-navigation`, **versión exacta** (la última estable; sin `^`).
- Un test que inicializa la librería y genera una navmesh de un suelo de 4 × 4 m (dos
  triángulos).

Consulta el README y los tipos del paquete instalado para los nombres exactos de la API
(inicialización, generación «solo», consultas y destrucción). **Si el test no pasa en Vitest
(Node) tras un intento razonable, para y avisa a la coordinadora** con el error exacto: es el
punto abierto A5 de la spec y cambia el plan.

## 1. `@escaperoom/nav3d`

Depende de `recast-navigation` y de `@escaperoom/shared` (solo `schemas` y `packs`). No importa
nada de Node ni del DOM.

### 1.1 `src/config.ts`

```ts
export const NAV3D = {
  cellSize: 0.15,
  cellHeight: 0.1,
  agentRadius: 0.3,
  agentHeight: 1.8,
  agentMaxClimb: 0.25,
  agentMaxSlopeDeg: 45,
  /** Tolerancia al ajustar un punto pedido a la navmesh. */
  snapPlan: 0.35,
  snapHeight: 0.5,
} as const;
```

Convierte estos valores a las unidades que pida recast (algunos parámetros van en celdas).

### 1.2 `src/input.ts` — geometría de entrada (puro, sin recast)

```ts
export interface NavInput { positions: Float32Array; indices: Uint32Array }

/** Triángulos de un colisionador en coordenadas del modelo (Three: X = x, Y = h, Z = y). */
export function colliderTriangles(collider: Collider3D): { positions: number[]; indices: number[] };

/** Geometría de toda una habitación (specs/27 §5.1). */
export function buildNavInput(
  pkg: RoomPackage,
  roomId: string,
  catalog: Models3DCatalog | undefined,
): NavInput;
```

- `box`: 8 vértices, 12 triángulos.
- `ramp`: cuña de 6 vértices. La cara superior sube de `h0` a `h1` avanzando en `dir`; la base
  está en `h = 0`.
- Cada colisionador se transforma con la pieza u objeto que lo lleva: escala uniforme, giro
  `yaw` (rotación sobre el eje vertical: `rotation.y = yaw · π / 180`) y traslación `(x, h, y)`.
- Orden de los vértices: caras hacia fuera (recast descarta las caras que miran hacia abajo).
- Qué entra:
  - todas las `pieces` de `world3d.rooms[roomId]`;
  - los `objects` de esa habitación que bloquean: todos **menos** los de `type === "puerta"`,
    los que tienen `leadsTo` y los que son placa de algún `simultaneous_plates`
    (`puzzle.plates[].objectId`). Modelo: el del `initialState` si ese estado declara `sprite`;
    si no, `object.sprite`.
  - El modelo se resuelve con `resolveModel3D(id, catalog, pkg.world3d?.models)`. Un modelo
    desconocido no aporta geometría.
- Si la habitación no existe o no hay geometría, devuelve arrays vacíos.

### 1.3 `src/nav.ts`

```ts
export interface NavPoint { x: number; y: number; h: number }   // coordenadas lógicas (§2)

export interface RoomNav {
  /** Punto de la navmesh más cercano dentro de la tolerancia, o `null`. */
  closest(p: NavPoint, tol?: { plan: number; height: number }): NavPoint | null;
  /** Ruta de `from` a `to` (ambos se ajustan antes a la navmesh). `null` si no hay. */
  path(from: NavPoint, to: NavPoint): NavPoint[] | null;
  /** Avanza de `from` hacia `to` deslizándose por los bordes; devuelve dónde acaba. */
  slide(from: NavPoint, to: NavPoint): NavPoint;
  /** `true` si la navmesh no tiene ningún polígono. */
  readonly empty: boolean;
  destroy(): void;
}

/** Inicializa recast (WASM). Idempotente: llamadas repetidas comparten la misma promesa. */
export function initNav3D(): Promise<void>;

/** Requiere `initNav3D()` resuelto. Con entrada vacía devuelve una `RoomNav` con `empty: true`. */
export function createRoomNav(input: NavInput): RoomNav;

/** Atajo: `createRoomNav(buildNavInput(...))`. */
export function createRoomNavFor(pkg: RoomPackage, roomId: string,
  catalog: Models3DCatalog | undefined): RoomNav;
```

La conversión entre coordenadas lógicas `(x, y, h)` y las de recast `(X = x, Y = h, Z = y)` se
hace solo dentro de este archivo. `closest` usa por defecto `NAV3D.snapPlan` y `snapHeight`.

### 1.4 `src/index.ts`

Reexporta `config`, `input` y `nav`.

### 1.5 Tests (`packages/nav3d/test/`)

Catálogo de prueba hecho a mano en `test/fixtures/catalog.ts`: `suelo` (caja 1×1×0,1 con la cara
superior en 0), `muro` (caja 1×1×2,4), `escalon` (caja 1×1×0,2), `rampa` (cuña 1×2, de 0 a 0,4,
`dir: "y+"`), `tarima` (caja 1×1×0,4). Helper `room(pieces, objects?)` que monta un `RoomPackage`
3D mínimo.

- `colliderTriangles`: número de vértices y triángulos; la cuña sube en el sentido correcto para
  las cuatro `dir`.
- `buildNavInput`: aplica giro y traslación (una caja girada 90° intercambia sus medidas en
  planta); excluye puertas y placas; ignora modelos desconocidos.
- Suelo de 6 × 6: `closest` en el centro devuelve el punto; fuera del suelo, `null`.
- Suelo con un muro en medio: `path` rodea el muro (más de dos puntos); `slide` contra el muro no
  lo atraviesa.
- Escalón de 0,2 m: se puede subir (`path` existe y acaba en `h ≈ 0,2`).
- Tarima de 0,4 m sin rampa: no se puede subir (`path` es `null`). Con la rampa al lado: sí.
- Habitación vacía: `empty === true`, `closest` devuelve `null`.
- Determinismo: generar dos veces la misma habitación da los mismos resultados en diez puntos de
  consulta.

## 2. Servidor de partida (`packages/colyseus-server`)

Añadir `@escaperoom/nav3d` a sus dependencias.

### 2.1 Estado (`src/schema/game-state.ts`)

`GamePlayerState`: añadir `h: t.number()` y `yaw: t.number()`. Valen 0 en salas 2D.

### 2.2 Constantes (`src/constants.ts`)

```ts
/** Salto máximo por mensaje `move` en una sala 3D, en metros (specs/27 §5.4). */
export const GAME_MAX_STEP_3D = 1.5;
/** Diferencia máxima de altura con una puerta para cruzarla en 3D. */
export const GAME_DOOR_REACH_HEIGHT_3D = 1.5;
```

### 2.3 Movimiento (`src/movement.ts`)

Añadir, sin tocar `validateMove`:

```ts
export interface Vector3 { x: number; y: number; h: number }

export interface Move3DLimits {
  maxDistance: number;
  /** Punto de la navmesh más cercano, o `null` si el pedido queda fuera. */
  closest(p: Vector3): Vector3 | null;
}

export type Move3DResult = { ok: true; position: Vector3 } | { ok: false; error: MoveErrorCode };

export function validateMove3D(current: Vector3, requested: Vector3, limits: Move3DLimits): Move3DResult;
```

Orden: valores no finitos → `OUT_OF_BOUNDS`; `closest(requested) === null` → `OUT_OF_BOUNDS`;
distancia en 3D entre `current` y el punto ajustado `> maxDistance` → `MOVE_TOO_FAST`; si no,
`ok` con el punto ajustado. Es puro: no importa `nav3d`.

### 2.4 `GameRoom` (`src/rooms/game-room.ts`)

- `setupRoom`: si `dimensionOf(roomPackage.meta) === "3d"`, `await initNav3D()` y guardar
  `this.catalog = getModels3DCatalog(roomPackage.map.tileset)`.
- `private navs = new Map<string, RoomNav>()` y `private navFor(roomId): RoomNav` que la crea la
  primera vez con `createRoomNavFor(this.roomPackage, roomId, this.catalog)`.
- `onDispose`: destruir todas las `RoomNav`.
- `movePayload`: añadir `h: z.number().finite().optional()` y
  `yaw: z.number().finite().min(0).lt(360).optional()`.
- `handleMove`, tras resolver el cambio de habitación (que no cambia de sitio), si la sala es 3D:

  ```ts
  const nav = this.navFor(current.roomId);
  const result = validateMove3D(
    { x: current.x, y: current.y, h: current.h ?? 0 },
    { x: payload.x, y: payload.y, h: payload.h ?? current.h ?? 0 },
    { maxDistance: GAME_MAX_STEP_3D, closest: (p) => nav.closest(p) },
  );
  ```

  Si falla, `this.fail(...)` igual que en 2D. Si va bien,
  `session.movePlayer(id, roomId, x, y, now, { h, yaw: payload.yaw ?? current.yaw ?? 0 })`.
  Con `nav.empty` (habitación sin suelo) se rechaza todo con `OUT_OF_BOUNDS`.
  En 2D, el código actual se queda exactamente como está.
- `handleRoomChange` en 3D: la distancia a la puerta se mide con `door.transform` en planta
  (`≤ GAME_DOOR_REACH`) y además `|current.h − door.transform.h| ≤ GAME_DOOR_REACH_HEIGHT_3D`.
  Al aparecer en la otra habitación se usan `h` y `yaw` del `spawnPoint`.
- Donde hoy se copia la posición de la sesión al estado (`player.x = position.x; player.y = …`),
  copiar también `player.h = position.h ?? 0` y `player.yaw = position.yaw ?? 0`. Hay varios
  sitios: localízalos buscando `player.roomId = position.roomId` y `player.roomId = previous.roomId`.

### 2.5 Tests (`packages/colyseus-server/test/`)

- `movement.test.ts`: casos de `validateMove3D` (válido, fuera, demasiado lejos, no finito; el
  resultado es el punto ajustado).
- `game-room-3d.test.ts`, con los mismos helpers que `game-room.test.ts` y un paquete 3D de dos
  habitaciones (suelo 6×6 cada una, un muro, una puerta abierta con `leadsTo`, una placa) y un
  catálogo de prueba inyectado:
  - un `move` válido actualiza `x`, `y`, `h` y `yaw` del estado;
  - un `move` dentro de un muro → `OUT_OF_BOUNDS`;
  - un `move` de 3 m → `MOVE_TOO_FAST`;
  - cruce de habitación cerca de la puerta: aparece en el spawn destino con su `h` y `yaw`;
    lejos de la puerta: `ROOM_LOCKED`;
  - una sala 2D (el Rey Aldric) sigue moviéndose como antes y su estado lleva `h = 0`, `yaw = 0`.

Para inyectar el catálogo de prueba, `GameRoom` lo obtiene con un método protegido
`protected models3DCatalog(packId: string)` que por defecto llama a `getModels3DCatalog` y que
el test sobrescribe en una subclase (mismo patrón que otros métodos protegidos de la clase).

## 3. Cliente de sesión (`packages/game-runtime/src/session/`)

- `protocol.ts`: `export const GAME_MAX_STEP_3D_M = 1.5;` (espejo del servidor; añádelo al test
  de `web` que comprueba que las constantes no divergen).
- `types.ts`:
  - `GamePlayerSnapshot`: `h: number; yaw: number`.
  - `GameActions.move(x, y, roomId?, extra?: { h?: number; yaw?: number })`.
- `snapshot.ts`: proyectar `h` y `yaw` (0 si el estado no los trae).
- `network.ts`: `move` envía `h` y `yaw` solo si vienen en `extra`.
- `local.ts` (cliente local del playtest sin servidor): en una sala 3D acepta el movimiento sin
  navmesh (no valida; el cliente ya se ciñe a su navmesh) y guarda `h` y `yaw`. En 2D no cambia.
- `packages/game-runtime/src/phaser/room-scene.ts`: `ScenePlayer` gana `h?: number` y
  `yaw?: number` (solo el tipo; Phaser los ignora).
- `packages/web/src/components/game-session/hooks/use-scene-sync.ts`: pasar `h` y `yaw` en
  `setPlayers(...)`.

Tests: los existentes de `snapshot` y `network` con los campos nuevos; uno de `local` en 3D.
